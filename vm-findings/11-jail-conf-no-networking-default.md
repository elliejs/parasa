# Default `jail.conf` never enables networking — containers have no network access

**File:** `recipes/jail.conf`
**Severity:** Bug — containers are unusable for their most common purpose
(running a network service) with the documented default configuration.

## The bug

`recipes/jail.conf`'s shared defaults section is:

```
exec.start = "/bin/sh /etc/rc";
exec.stop  = "/bin/sh /etc/rc.shutdown";
exec.clean;
mount.devfs;
devfs_ruleset = 4;
```

No `ip4`, `ip6`, or `vnet` parameter is set anywhere — neither here nor in
the per-container `jail.conf` generated by `new_container.sh`
(`create_container_recipe_extras()`, which only writes `host.hostname`,
`path`, and `mount.fstab`). FreeBSD's `jail(8)` default for `ip4`/`ip6`
when unset is `disable`, not `inherit` — confirmed via
`jail -p demo1` showing `ip4=disable ip6=disable` on a container started
exactly per the documented recipe.

With networking disabled, essentially anything server-shaped is
impossible out of the box: no `pkg` (DNS/HTTP both fail with `Protocol
not supported` on any socket call), no outbound connections, nothing
listening reachable from outside the jail.

## How we hit it

Tried to install and run nginx inside container `demo1` (started per the
documented `jail(8)` flow) as a way to generate real "drift" to exercise
the save/update pipeline. `pkg bootstrap` failed with DNS resolution
errors; isolated it to the socket layer, not just DNS, via `jexec demo1
fetch http://<raw-ip>/` also failing with `Protocol not supported`, and
`jls -j demo1 -o ...` / `jail -p demo1` confirming `ip4=disable
ip6=disable`.

## Suggested fix

Add networking to the shared defaults in `recipes/jail.conf` — at
minimum `ip4 = inherit;` (classic shared-stack jails, matching how the
rest of the framework already treats containers as trusted-by-default
local services, no `vnet`/bridge complexity implied) so containers get
usable network access without every container's `jail.conf` needing to
repeat it. If per-container IP isolation is eventually wanted, that's a
bigger design question (vnet + bridge/epair setup) — but *some* default
that isn't "no network at all" seems necessary for containers to be
useful as shipped.
